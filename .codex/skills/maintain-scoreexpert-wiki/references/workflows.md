# ScoreExpert Wiki 工作流

## 目录

- 导入来源
- 查询与沉淀
- Lint 与审核
- 冲突与状态迁移
- 精简、删除与归档
- Git 维护

## 导入来源

1. 判断来源类型：网页或文本放入 `raw/articles/`，论文或 PDF 放入 `raw/papers/`，会议或访谈放入 `raw/transcripts/`，图片放入 `raw/assets/`。
2. 保存完整来源内容并加入 raw frontmatter。URL 记录 `source_url`；本地文件记录 `source_path` 和原文件 SHA-256。
3. 计算第二个 `---` 之后正文的 SHA-256，写入 `sha256`。可用：

   ```bash
   awk 'BEGIN { n=0 } /^---$/ { n++; next } n >= 2 { print }' raw/articles/<file>.md | shasum -a 256
   ```

4. 重复导入同一路径或 URL 时先比较哈希。内容不变则跳过；内容变化则新增带日期或时间戳的快照，不覆盖旧文件。
5. 在自行推导前，检查来源是否存在明确结论，并按下方“经验提取模式”选择一种或组合使用；不预设经验条数，也不要求来源使用固定标题。
6. 把所有经验、证据和假设候选先写入审查队列，不要边读边直接写正式页。使用下方“经验候选审查门槛”逐条记录判定和理由。
7. 搜索 `index.md`、对应优化目标总览和所有具体经验卡，用“触发条件 + 动作 + 机制 + 观测 + 边界”判断是否真正重复；参数元组相同不等于经验相同。
8. 先选择优化目标，再选择 `experience_category`。新知识能写入现有目标总览或具体经验卡时直接更新原页；只有主题出现于两个以上来源、或是单一来源核心主题且具有不可替代价值时才创建新页。不要创建分类总览、独立 Score 页或通用验证页来重复经验卡内容。
9. 使用 `SCHEMA.md` 规定的 frontmatter 和标签；单一来源或变化较快的结论使用 `confidence: medium` 或 `low`。证据缺口影响置信度和边界，但不得删除或改写来源明确表达的经验。
10. 若创建或更新正式经验，在 frontmatter 记录 `status`、`optimization_priority`；active 页再记录 `admitted_by` 和 `admitted_at`。正文只写“1. 场景描述”和“2. 具体的并行策略”两个一级章节：第一章写拓扑、异构、模型/映射约束、硬匹配和不适用条件；第二章只使用“部署策略、部署经验、失效条件与回退”，把执行步骤并入部署策略，把适用范围留在第一章，不重复治理信息。
11. 对三种证据分栏：`score` 推导、拓扑推理、真实 Evaluation。没有 Evaluation 时保留证据缺口，但不要让审计内容淹没部署动作。任何来源没有明确陈述的拓扑解释或综合判断，标记为“Wiki 补充推理”。
12. 对照检查：来源的每条显式经验是否都在知识页中出现；知识页是否把新增推理误写成来源结论。
13. 至少添加两个出站 wikilink，并检查相关旧页是否需要回链。
14. 新增或修订具体经验卡时，同步更新对应优化目标总览和总经验库状态；局部/分布式异构知识按“场景定义 → 异构影响 → 并行策略 → 场景案例”组织，把隔离、均衡与对称对策融入具体并行维度，具体卡数和参数写入独立的场景案例。准入状态、审核记录和证据完整度只写具体经验卡，不在场景案例重复。
15. 按字母或领域顺序更新 `index.md` 的摘要、总页数和日期。
16. 向 `log.md` 追加 `ingest` 或 `update` 记录，列出所有创建和更新的文件。

### 经验提取模式

1. **显式提取**：来源存在“经验总结”“结论”“建议”“最佳实践”“推荐”或语义等价段落时，提取实际存在的 N 条结论，N 可以是 1 或任意数量。保留原顺序、限定词、因果关系，以及比例、阈值、上下界、不等式等定量关系。
2. **分散归纳**：来源没有总结段落，但在分析、表格或实验结果中分散给出明确决策时，只合并来源能够直接支持的规则，标记为“来源分散归纳”，并指出对应证据位置。不要把 Wiki 推断混入其中。
3. **无结论推导**：来源只有场景、候选或数据，没有部署结论时，允许基于 score、拓扑或 Evaluation 生成“Wiki 推导假设”。逐项标记推导链和缺口，默认进入 `unverified`，不能伪装成来源经验。
4. **混合来源**：同一文件可能同时包含明确经验和未总结证据。先完整保留明确经验，再把新增归纳或推导分别标为“来源分散归纳”或“Wiki 补充推理”。

经验粒度由决策决定：共享同一触发条件、动作和机制的内容合并为一条；触发条件或部署动作不同则拆开。不得为了固定格式强行生成四条、五条或任何预设数量。

定量关系与具体实例同时保存：把 `TP:DP≈2:1` 写成经验规则，把 `TP=8,DP=4` 写成当前约束下的实例。索引摘要优先呈现可迁移的关系，不能只展示实例或模糊趋势。

批量导入时先读完全部来源，再统一识别主题、搜索现有页面、写页面、更新一次索引和一次日志。若会修改 10 个及以上已有页面，先确认范围。

### 经验候选审查门槛

每个候选必须记录 `candidate_id`、来源、场景、原文或归纳内容，并依次检查：

1. **来源可追溯**：能定位到 raw 来源和场景；否则 `REJECT`。
2. **触发条件具体**：至少包含拓扑、慢卡数量/位置/倍率、模型或 score 条件中的关键项；空泛触发 `REJECT`。
3. **部署动作可执行**：给出 PP/TP/DP/MBN 或 rank/group/stage 的具体动作；只有“应该优化”“选择高分候选”时 `REJECT`。
4. **非 score 机制**：解释同步范围、流水线瓶颈、replica skew、显存或通信层级。纯粹重复“score 高所以好”的内容标为 `EVIDENCE_ONLY`。
5. **预期观测可检查**：给出 latency、throughput、显存、group/stage/replica time、skew 或 OOM 等指标；缺失时不得成为 active。
6. **失效边界明确**：说明什么场景变化或反证会停止复用；没有边界的通用化表述 `REJECT` 或改写后重审。
7. **有新增价值**：与已有经验比较。参数相同但触发、机制或验收不同可以分开；仅重复参数和结论时合并或 `REJECT`。
8. **证据与状态匹配**：默认情况下 score-only 为 `EVIDENCE_ONLY`，具体且可证伪但缺证为 `KEEP_FOR_VALIDATION`；知识库所有者明确确认经验成熟时，人工审核可将其判为 `ACCEPT_EXPERIENCE`。写入 `active` 前仍须补齐边界、直接推理契约、审核日期，并保留来源附件缺口。

来源明确经验即使未通过正式经验门槛，也必须在来源整理和证据层保留，不得借筛选之名删除。审查只决定它进入知识库后的角色。

当用户要求查看演化过程时，每个输入批次保存一个阶段快照，使用模板中的“经验库阶段快照”。快照放入 `outputs/`，不自动加入正式页索引；人工确认后再按正常写入门禁更新知识页。

## 查询与沉淀

1. 先从 `index.md` 进入优化目标框架和对应目标总览，再读取匹配的具体经验卡；页面超过 100 个时用 `rg -n '<关键词>' . -g '*.md'` 补充搜索。
2. 以“优化目标 → 场景分类 → 资源/拓扑/异构硬条件 → 模型与映射约束 → 量化边界 → 具体经验卡”的顺序核对，区分 active 结论与 `unverified`、`partially_supported` 内容。
3. 唯一命中 `active` 卡且全部硬条件和边界匹配时，直接输出主策略、`PP/TP/DP/MBN`、映射、置信度和回退，不要求真实 Evaluation；同时引用实际 Wiki 页面。
4. 优先把跨实例总体经验写入目标总览，把案例实例写入具体经验卡及总览的“场景案例”；案例直接使用业务名称，不添加“单场景经验”等重复标签。只有不能被这三层容纳的独立对比或查询结论才写入 `queries/` 或 `comparisons/`；简单查找不落盘。
5. 未命中、越界、冲突、关键字段缺失或只命中非 active 卡时，不直接部署；输出候选、缺口和最小仿真/Evaluation/审核补库任务。经验库为空时明确说明，不编造结论。
6. 落盘时使用模板、补双向链接、更新 `index.md` 和 `log.md`。

新场景至少回答：推理模式（直接经验或补库）、场景设置、命中经验、部署策略与映射、适用边界、失效条件、置信度和回退。只有进入补库模式时才附 score/拓扑/Evaluation 证据缺口和最小验证任务。部署经验总结使用“触发条件 → 部署动作 → 作用机制 → 预期观测 → 失效边界”，不能用分析过程代替经验规则。

## Lint 与审核

运行：

```bash
python3 scripts/lint_wiki.py
```

按优先级处理：

1. 结构错误：断链、孤立页、缺失索引、frontmatter 缺失、未知标签、raw SHA 不匹配。
2. 来源漂移：上游文件变化时新增快照，不修订旧 raw 文件。
3. 审核项：`confidence: low`、`contested: true`、超过 200 行页面和日志轮换。
4. 人工语义审核：相同场景是否出现不兼容策略、是否把假设写成了结论、是否混淆 score 与 Evaluation。
5. 经验可用性审核：active 页面是否有独立的“部署经验总结”，部署动作能否脱离推导过程直接执行，机制、观测和失效边界是否与动作一一对应。
6. 来源保真审核：提取模式是否与来源结构一致；显式结论是否逐条保留原顺序、限定词和定量关系；比例/阈值是否被具体实例或模糊措辞取代；分散归纳与 Wiki 推理是否分开；是否为了模板凑数或强拆经验。

修复后再次运行 lint，并向 `log.md` 追加 `lint` 记录。结构错误必须为 0；审核项可以保留，但要记录原因。

## 冲突与状态迁移

1. 比较来源日期、哈希验证状态、场景条件和 Evaluation 直接性。
2. 条件不同但结论不同不一定是冲突；优先拆成明确场景分支。
3. 真正冲突时保留双方陈述，设置 `contested: true`，并填写 `contradictions` slug。
4. 不静默覆盖旧结论。active 经验被替代时保留生命周期和历史页面。
5. 未验证原因先写成可证伪假设，列出替代解释、指标、最小效应阈值和仿真计划。
6. supported 假设只能生成正式更新提案；等待审核门禁完成后再更新 active 页面。

## 精简、删除与归档

1. 先列出用户明确要求保留的文件，再用 `rg` 找出候选删除页的全部入链、出链、来源和规则依赖；范围不明确时先确认准确文件列表。
2. 默认保留 `raw/` 不可变来源、候选审查与状态演化记录，以及 `outputs/experience-evolution-demo/`。只有用户明确点名时才删除来源或演化快照。
3. 页面内容已完整合并到目标总览或具体经验卡、且用户要求永久删除时，使用删除；仍需保留历史生命周期时才移入 `_archive/`。
4. 删除重复汇总或支撑页时，把必要的 score 推导、验证指标、证据状态和回退规则先并入目标总览或具体经验卡，不能因删页丢失知识。
5. 同步清理所有 wikilink、`index.md`、`SCHEMA.md`、Skill 模板和 linter 中的旧强制规则；不要让校验器继续要求已删除页面。
6. 向 `log.md` 追加 `delete` 或 `archive` 记录，写清删除项、保留项、替代页面和可恢复性。
7. 运行 lint 和 `git diff --check`，确认没有断链、孤立页、索引遗漏或错误页数。

## Git 维护

只在用户明确要求 Git 写操作时提交、建分支或推送。

1. 运行 `git status --short --branch` 和 `git diff`，识别并保护用户已有改动。
2. 运行 Wiki lint 与 `git diff --check`。
3. 只暂存本次任务范围内文件；核对 `git diff --cached --stat` 和必要内容。
4. 使用描述知识变化的提交信息，例如 `docs: add deployment experience`。
5. 提交后确认工作区状态和提交哈希。只有用户明确要求并且远端已配置时才推送。
