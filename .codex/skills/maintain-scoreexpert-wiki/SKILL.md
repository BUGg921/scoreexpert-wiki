# 维护 ScoreExpert 部署经验 Wiki

## 目标

维护一个持续积累、来源可追溯、结论有边界的 ScoreExpert 部署经验 Wiki。把验证成本沉淀在经验准入阶段，使后续匹配新场景可以直接推理部署策略，而不是每次重新运行真实 Evaluation 或从原始材料推导全部知识。

从包含 `SCHEMA.md`、`index.md` 和 `log.md` 的项目根目录执行命令。若当前目录不确定，先运行 `git rev-parse --show-toplevel` 并切换到返回目录。

## 当前知识结构

使用“总经验库 → 优化目标总览 → raw 场景来源”的当前结构，不插入重复的分类汇总或具体经验卡层：

```text
concepts/deployment-objective-knowledge-framework.md
└── concepts/<optimization-priority>-experience-summary.md
    └── raw/articles/<scenario-source>.md
```

- 总经验库永久保留延迟优先、稳定优先及各自三类场景的完整框架；优化目标总览只为已有总体经验的目标创建，不为暂时空白的目标预建独立空总览。
- 场景分类只使用同构基线、局部异构、分布式异构；分类规则和数值策略写入目标总览，具体场景细节保留在唯一 raw 来源。
- Score 推导、映射、验证指标和结论边界写入 raw 场景来源；目标总览只保留可直接召回的定义、数值策略、原因和场景链接。
- `raw/` 保存不可变来源，`outputs/experience-evolution-demo/` 保存审核演化；精简知识页时默认保留二者，除非用户明确点名删除。

## 每次任务先定向

在读取、查询或修改页面前，按顺序执行：

1. 读取 `SCHEMA.md`，确认领域、frontmatter、标签和状态规则。
2. 读取 `index.md`，确认已有页面及其摘要。
3. 读取 `log.md` 最近 20–30 条记录，了解近期操作。
4. 运行 `git status --short --branch`，识别用户已有改动并保护它们。
5. 用 `rg` 搜索当前主题；页面超过 100 个时必须同时按文件名和正文搜索。

不要跳过定向步骤。不要创建已有主题的近义重复页。

## 选择操作

- 导入文件、URL、场景、报告或 Evaluation：读取 [工作流](references/workflows.md) 的“导入来源”，创建文件时同时读取 [模板](references/templates.md)。
- 回答部署问题或沉淀新分析：读取 [工作流](references/workflows.md) 的“查询与沉淀”。
- 检查 Wiki 健康状态：读取 [工作流](references/workflows.md) 的“Lint 与审核”。
- 处理冲突、经验覆盖或合并：读取 [工作流](references/workflows.md) 的“冲突与状态迁移”。
- 精简、删除或归档页面：读取 [工作流](references/workflows.md) 的“精简、删除与归档”。
- 用户明确要求提交、建分支或推送时：读取 [工作流](references/workflows.md) 的“Git 维护”。

## 不可违反的知识边界

- 把 `raw/` 视为不可变来源层。来源变化时新增带日期的快照，不修改旧快照。
- Evolve 仿真完成后只把带场景名和时间戳的 `*_scenario_analysis.md` 平铺保存在 `DAGBuilder_Evolve/outputs/` 根目录作为待审草稿，不保留成功运行的场景子目录；仿真完成不等于来源准入。只有知识库所有者明确表示已手动修改、审核完成并授权入库后，才能把该平铺文件的当前版本导入 `raw/`。
- 用户审核后的 raw 快照是后续 `concepts/` 更新的唯一文本来源。不得从未审核的仿真草稿、`deployment_experience.json` 或 `final_report.json` 直接修改 concepts。
- 只把目标总览中已经成熟并有唯一 raw 来源支撑的场景规则写成部署第一候选。
- 在线查询命中唯一成熟场景，且优化目标、场景分类、资源拓扑、异构分布、模型约束、映射能力和 raw 量化边界完整匹配时，直接输出部署策略与回退，不要求新的真实 Evaluation。未命中、越界或冲突时，停止直接部署并生成补库任务。
- 当前不创建重复的具体经验卡；目标总览承担召回规则，raw 来源承担场景描述、Score、具体映射和结论边界。
- 来源若已有“经验总结”“结论”“建议”或“最佳实践”等显式结论，按原顺序和原语义并入“具体的并行策略”。不得用重新推导替代、降级或淹没来源结论；Wiki 新增推理必须另行标注，不能写成来源原话。
- 不预设经验数量、标题或排版。按来源选择“显式提取、分散归纳、无结论推导”模式；一条或多条都可以，以独立的触发条件和部署动作为经验粒度，不为填模板强拆或凑数。
- 正式写入前必须经过候选审查：先保存筛选前候选，再按“来源、触发条件、部署动作、非 score 机制、预期观测、失效边界、新增价值、证据状态”逐条判定。纯 score 解释只进入证据层；空泛、重复、过度外推或不可执行内容不得进入经验层。
- 每个场景必须按 `SCHEMA.md` 归入同构基线、局部异构或分布式异构；Score 证据和验证方法写入对应 raw 来源，不冒充第四类经验。
- 组织或回答经验库时先选择优化目标入口：延迟优先或稳定优先；再进入同构基线、局部异构或分布式异构。优化目标不替代 `experience_category`，同一经验也不能因换入口而复制或无证据升级。
- 延迟优先经验沉淀时必须明确 latency 目标和吞吐/显存/稳定性护栏；稳定优先经验必须明确方差、尾延迟、OOM/失败率、超时或恢复指标和性能下限。缺少相应证据时写成知识缺口，不生成直接部署结论。
- 优化目标总览保存在 `concepts/` 根目录，场景来源保存在 `raw/articles/`。移动来源后同步更新 Markdown 链接、frontmatter sources 和正文来源标记。
- 当前使用“总经验库 → 优化目标总览 → raw 场景来源”的结构。三类分支在“并行策略”中写成熟的变量化参数关系，在“场景案例”中概括边界并用普通 Markdown 链接指向唯一 raw 来源；具体参数数字、详细卡数、拓扑、rank 映射、Score 代码和结论边界保留在 raw。不得设置“当前经验范围”。
- 需要展示知识库演化时，按输入批次保存阶段快照，至少包含“本批输入 → 筛选前 → 判定与理由 → 筛选后 → 相比上一阶段的增删改”。不得只展示最终库而丢失中间过程。
- 把来源强调的比例、阈值、上下界、不等式和参数关系保留为定量经验；固定参数数字只保留在 raw。目标总览先定义变量，例如 `N` 为参与部署的 GPU 总数、`G` 为单节点可用 GPU 数，再用 `PP×TP×DP=N`、`TP≤G` 下的 TP/DP 联合候选、整数约束和最大/最小可行值表达关系。实例中的 TP 恰好与节点规模一致只能解释通信边界，不能写成 `TP=G` 规则。
- 三类知识严格分工：场景定义只用输入可见的物理异构特征完成分类；每条并行策略先写可直接判定的适用规则，再依次写资源使用、`PP`、`TP`、`DP`、`MBN` 五项变量化关系，不写某次实验的固定参数数字。适用规则只使用输入中的慢卡数量、rank、物理位置、节点/亲和组慢卡向量和速度倍率，负责判断选择哪条策略；不重复所在总览的优化目标，也不写 raw 边界、模型/workload、显存、网络、映射能力或参数整数可行性，这些留到选中策略后的部署校验。满卡写成 `active_gpu=N`，留卡必须给出可计算规则。场景案例只链接 raw；具体数值、实际映射、layer/计算量分配和验收细节都保留在 raw。变量化必须能从 raw 的参数原因直接推出，不得为了可迁移性补造关系或扩大适用边界。
- 并行策略按资源使用、`PP`、`TP`、`DP`、`MBN` 五项变量化关系去重：五项全部相同就合并为一个策略编号，适用规则用“或”保留各个已准入输入模式，并把机制、观测和边界差异分别保留在该编号的“原因”和“场景案例”；任一项不同就拆成独立策略，并按“最小 PP、TP 主导”或“深 PP、最小 TP 双副本”等参数特点命名，不按场景编号凑分支。
- 当前成熟经验的参数关系：同构使用最小 PP、`TP:DP=2:1` 的满卡组合和最小 MBN；单张局部慢卡使用最小局部 TP、最小 DP、由 `PP=N/(TP×DP)` 得到的满卡深 PP，以及约束内最大 MBN；两张跨亲和组慢卡与四张均匀慢卡共用“最小 PP、TP 主导型满卡方案”，其 replica 等待或对称机制分别保留；五张 2/1/1/1 非对称慢卡使用不同的“深 PP、最小 TP 双副本方案”，即满卡、最小 TP、`TP:DP=1:2`、`PP=N/(TP×DP)` 和单位 microbatch 关系 `MBN=B/DP`。所有关系仍受各自 raw 边界约束，不自动准入新资源规模。
- 通信、隔离、流水线气泡和 DP 等待等机制统一写入独立的“原因”，用于解释资源使用以及 `PP`、`TP`、`DP`、`MBN` 的选择，不能与数值策略混写。“原因”必须与“并行策略”按编号一一对应。
- 目标总览的“场景定义”和“场景案例”使用无序列表；“并行策略”和“原因”按编号一一对应。每条并行策略依次写适用规则、资源使用、`PP`、`TP`、`DP`、`MBN`；每条原因先写加粗分支名，再用同级缩进的二级圆点解释相应选择。原因中不设置“适用边界”圆点，也不放 raw 链接；边界和映射保留在 raw，来源链接统一放在场景案例。
- 正式经验总览和经验页不得提评分策略、评分权重、打分公式或 score 选择过程；原因只保留算力利用、显存、通信、同步等待、流水线气泡、replica skew 和调度等部署机制。评分代码与候选排序证据只留在 raw 和审核层。
- 优化目标总览中的同构基线、局部异构和分布式异构固定使用“场景定义 → 并行策略 → 原因 → 场景案例”。场景案例概括条件、数值结果并链接唯一 raw 来源；没有成熟经验的目标保留结构和知识缺口，不编造数值策略或原因。
- 目标总览的“场景定义”直接描述物理场景，不写“由案例归纳”“当前案例不是门槛”等编写过程说明：同构描述无稳定设备快慢差异；局部异构必须写清异常是否稳定可识别、rank/速度/物理位置是否已知、异常是否全部位于同一节点或另一个由 raw 明确准入的单一物理局部范围，以及局部范围外是否仍无固定快慢结构；分布式异构按节点慢卡向量和亲和组慢卡向量判断异常是否覆盖多个独立物理区域，不能用慢卡总数单独判定。适用规则进一步用精确的慢卡数量、节点/亲和组分布和速度特征选择策略；实际 group/stage/replica 和 layer 映射仍属于 raw 边界。
- 卡数、节点规模和拓扑属于场景匹配条件；资源变化后先重新判定同构/局部异构/分布式异构类别并重建完整并行拓扑。若成熟策略明确给出卡数换算规则，且能够求得满足模型、比例和通信边界的完整整数拓扑，则允许直接生成新参数；否则按新场景补库。不能把减卡当作随意删除 rank 或照搬原实例参数。
- 把 `unverified`、`partially_supported`、`mixed` 等假设留在验证层，不要改写成正式经验。
- 经验成熟度与来源附件完整度分开判断。知识库所有者对明确点名的报告说“审核通过”时，默认同时授权导入该报告的当前版本并确认经验成熟，判定为 `ACCEPT_EXPERIENCE` 并写入目标总览；只有所有者明确要求暂不写入、仅保留证据或待验证时才停止或降级。同时必须在 raw 来源中保留硬条件、参数、原因和结论边界，并如实记录缺失的原始指标。
- 没有知识库所有者的明确成熟确认时，即使假设达到 `supported`，也只生成更新提案；仍需人工审核、dry-run 和显式写入。
- 分开陈述 score 证据、拓扑推理和真实 Evaluation 证据。缺少 Evaluation 时直接写明，不要补造。
- 把参数组合绑定到总卡数、每节点卡数、亲和组、慢卡数量/位置/速度倍率、rank mapping、模型约束和搜索空间。
- MBN 最优值命中搜索空间上界时，在目标总览写成“约束内最大可行值”，在 raw 保留具体上界数字；不得写成物理必然最优。
- 每个知识页至少保留两个出站 `[[wikilinks]]`，并检查相关旧页面是否需要反向链接。
- 只使用 `SCHEMA.md` 已登记标签。需要新标签时先更新 schema。
- 每次新增 raw 场景快照时同步维护对应优化目标总览、`index.md` 和 `log.md`；raw 变化时新增带日期快照而不修改旧快照，删除页面时同步清理所有入链和已废弃的强制规则。
- 若一次导入将修改 10 个及以上已有页面，先向用户确认范围。

## 使用项目能力

把这些文件视为当前权威接口：

- `SCHEMA.md`：页面、标签、来源和状态契约。
- `index.md`：页面目录与查询入口。
- `log.md`：追加式操作历史。
- `raw/`：不可变来源快照。
- `scripts/lint_wiki.py`：零第三方依赖的结构与来源健康检查。

不要在 skill 内复制 `scripts/lint_wiki.py`；直接使用项目版本，保证检查规则只有一个来源。

## 验证与交付

完成任何写操作后运行：

```bash
python3 scripts/lint_wiki.py
git diff --check
git status --short --branch
```

把结构错误修到 0。逐项解释 review item；低置信度假设可以保留，但必须是有意且与页面状态一致。

最终说明：创建或更新了哪些文件、来源与置信度如何变化、lint 结果、仍待验证的内容。不要因为修改完成就自动提交或推送；只在用户明确要求 Git 写操作时执行。
